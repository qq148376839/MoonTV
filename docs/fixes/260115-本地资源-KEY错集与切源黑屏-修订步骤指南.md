## ✅ 2026-01-16 回归修复补充（文档与现状对齐）

本段用于对齐“实际代码行为”，避免出现“文档说已修、实际回退”的情况：

1. **不再依赖 `config.json`**

   - `pnpm dev` 不再要求 `config.json` 存在（缺失时生成最小 `runtime.ts`）。
   - 播放页的官方/非官方判定优先使用 `SearchResult.source_type`（由搜索链路写入），不再依赖 `SourceConfig`。

2. **下载 KEY 落盘 + m3u8 改写已恢复**

   - 下载器会下载 key 到 `episode_XX/key_000.key` 并将 m3u8 内 `URI="..."` 改写为 `URI="episode_XX/key_000.key"`。
   - KEY 请求会强制 `no-cache` 且 `Referer=mediaPlaylistUrl`，并记录 `sha256` 指纹；若 key 内容变化会告警并覆盖写入（观测优先+自愈）。

3. **本地路由已支持 key 文件**

   - `src/app/api/[episode]/[segment]/route.ts` 支持 `key_000.key`（原先仅支持 `segment_*.ts`）。

4. **切集/切源稳定性：统一“销毁并重建”**
   - 播放页移除非 WebKit 的 `switch` 切源分支，切集/切源统一销毁旧 Hls/Artplayer 后重建，避免黑屏/不更新。
   - 本地资源模式下不再跳过 `updateVideoUrl`，否则会导致“无法切换剧集”。

## 2. 问题 A：下载 KEY 错集（本地播放）修订步骤

> 你当前已确认：`episode_04/key_000.key` 与 `episode_05/key_000.key` 内容一致。  
> 这说明“错 KEY”大概率发生在**下载落盘阶段**（写错/复用错/获取错），而不是 m3u8 中 `URI="episode_05/key_000.key"` 这种字符串改写错。

### 2.1 先做“事实判定”：上游是否真的不同 key？

目的：区分 **解析端/上游返回就错** vs **下载器写错**。

#### Step A1：确认本地 m3u8 的 KEY 引用（你已提供样例）

本地落盘 m3u8（示例）：

- 第 4 集：
  - `#EXT-X-KEY:...,URI="episode_04/key_000.key"...`
- 第 5 集：
  - `#EXT-X-KEY:...,URI="episode_05/key_000.key"...`

结论：URI 改写“表面正确”（指向各自 episode 目录）。

#### Step A2：对比本地 key 文件哈希（PowerShell）

在资源目录下执行（示例路径见你提供的 `data/videos/.../789caiji_91526/`）：

```powershell
Get-FileHash .\episode_04\key_000.key -Algorithm SHA256
Get-FileHash .\episode_05\key_000.key -Algorithm SHA256
```

- 若 **哈希相同**（你目前是这种情况）：继续 Step A3（抓上游 key）
- 若哈希不同：KEY 文件本身不同，则重点转向“TS/IV/播放链路是否走到本地 key”

#### Step A3：抓“上游 m3u8 与 key”做对照（强烈建议）

你需要拿到**第 4/5 集在“下载前/解析后”的真实 m3u8 URL**（上游或解析服务输出的 m3u8）。

推荐获取方式（任选其一即可）：

- **方式 1（最简单）**：在浏览器 Network 面板里找到该集的“真实 m3u8 请求”（不是本地 `episode_XX.m3u8`），复制 URL
- **方式 2（解析接口）**：对该集原始 episodeUrl 调用 `/api/parse` 拿到 `m3u8_url`

拿到后：

1. 下载上游 m3u8 内容（Windows 可用 `curl`）并找出 `#EXT-X-KEY` 的 `URI=...`
2. 分别请求第 4/5 集的 key URL，计算响应内容 SHA256
3. 将“上游 key hash”与“本地 key_000.key hash”对比

判定口径：

- **上游第 4/5 集 key hash 不同**，但本地两集 key hash 相同 ⇒ **下载器写错/复用错**（进入 2.2）
- **上游第 4/5 集 key hash 相同** ⇒ 上游本来就复用 key；“播放失败”更可能是 **TS 不匹配/片段缺失/其它解密参数差异**（进入 2.3）

### 2.2 若确认是下载器写错：修订方案拆解（按优先级）

#### 方案 A（优先）：落盘时记录“key 来源指纹”，并拒绝跨集污染

修改点（建议写入元数据/日志，便于长期定位）：

- 在 `src/lib/download-service.ts` 下载 key 后：
  - 计算 `sha256(keyBytes)`（或至少记录 `buf.length` + 前 16 bytes 的 hex）
  - 日志打印：`episodeIndex`、`keyUrl`、`keyFilePath`、`sha256`
- 在写入前：
  - 若 `key_000.key` 已存在且 hash 不同 ⇒ 覆盖写入，并打印告警（说明上次落盘不可信）

收益：即使上游偶发变更 key，也能快速定位“写错发生在哪一集/哪个 URL”。

### 2.2.1（已实施，2026-01-15）观测优先的落地修复点

> 目标：先**观测与自愈**，不直接强门禁阻断下载（后续若仍有问题再升级到强门禁）。

- **下载器 KEY 观测指纹**（`src/lib/download-service.ts`）：
  - 计算并打印 `sha256(keyBytes)`（同时记录 `episodeIndex/keyIndex/bytes/keyUrl`）
  - 若 `episode_XX/key_YYY.key` 已存在且 hash 不同 → **告警并覆盖写入**
- **KEY 请求强制 no-cache**（避免中间层缓存导致跨集复用旧 key）
- **KEY 请求 Referer 纠正**：将 KEY 请求的 `Referer` 设为 **当前媒体播放列表 URL（mediaPlaylistUrl）**
  - 背景：你已复现“第 5 集下载开始时 key 正确，下载完成后 key 漂移成第 4 集 key”
  - 典型根因：上游 key 接口对 `Referer`/防盗链敏感，`Referer` 不符合真实播放链路时可能返回“默认/上一集” key

#### 方案 B：确保 keyUrl 的解析与去重只作用于“单集”

检查点：

- `keyUrlToLocalRel`、`keyCounter` 必须是 **每次 downloadM3U8 调用内**的局部变量（当前实现是局部的）
- 确认没有其它层的缓存（例如 `fetchWithRetry` 内部做了“按 URL 缓存响应体”）

建议动作：

- 排查 `fetchWithRetry` 的实现：确认其不会复用上一次的响应 body（尤其是 key 响应）
- 若确实存在缓存：对 key 请求关闭缓存（例如 headers 加 `Cache-Control: no-cache`，或在 fetch 层禁用 memo）

#### 方案 C：补齐“每集 KEY 的一致性校验”

下载完一集后，在落盘前做一次校验：

- 从“下载前的原始 m3u8（clean 前或 clean 后都可）”提取 key URI
- 重新构造 keyUrl（absolute）
- 立刻再请求一次 key URL，比较与刚写入的 key_000.key 是否一致
  - 不一致：标记该集失败（不要写 `episode_XX.m3u8`），避免生成“必坏本地集”

### 2.3 若确认上游本来就复用 key：转向“TS/解密参数/缺片”排查

你提供的 `episode_04` / `episode_05` TS 段数量非常多（`segment_12xx`、`segment_15xx`），建议补做两项验证：

- **完整性**：确认该集 m3u8 映射的所有 `segment_XXX.ts` 均存在且 `size>0`
- **同一 key 下能否解密**：用 Hls.js 的 error details（如果能复现到 `decrypt`）定位是 key 还是 ts

（下载器已有“缺片校验 + 补偿重试”，但若写出了 m3u8，仍建议对“失败集”追加更强的校验门禁）

## 3. 问题 B：切换到本地后黑屏/需刷新 修订步骤

### 3.1 先判定“黑屏时播放器到底有没有在拉流？”

在 Chrome DevTools：

- **Network**：过滤 `m3u8` / `ts` / `key`
  - 若没有任何请求：播放器初始化/切源流程未触发（偏前端生命周期）
  - 若 m3u8 200 但 ts/key 不请求：Hls 未 attach 或解析失败
  - 若 ts/key 有 404/500：偏后端路由（`/api/[episode]/[segment]`）或文件缺失

建议额外检查：

- 直接访问：
  - `/api/episode_04/key_000.key`（应 200 且长度 > 0）
  - `/api/episode_04/segment_000.ts`（应 200）

### 3.2 重点怀疑点（与你的“刷新即好”特征匹配）

#### 怀疑点 B1：切源路径下，旧的 `video.hls` 未被销毁导致卡死

在 `src/app/play/page.tsx`：

- 非 WebKit 且播放器已存在时走 `switchUrl(videoUrl)` 分支
- 但该分支**不一定**会销毁旧的 `video.hls`

修订建议：

- 在执行 `switchUrl` 前，对 `artPlayerRef.current.video.hls` 做显式 `destroy()`（并置空）
- 或统一策略：不区分 WebKit/非 WebKit，切源都“销毁并重建播放器实例”（以稳定优先）

### 3.4（已实施，2026-01-15）稳定优先的切源与状态保留落地修复点

- **切源策略统一“销毁并重建”**（`src/app/play/page.tsx`）：
  - 移除非 WebKit 的 `switchUrl` 切源分支，避免旧 Hls 状态残留导致黑屏
  - 切源/命中本地前，显式 `destroy()` 旧 `video.hls` 后再销毁播放器实例
- **状态保留（以历史记录为准）**：
  - 进度：优先使用历史记录的 `play_time`（仅在“同一集数”匹配时生效），否则 fallback 到切源前 `currentTime`
  - 倍速/音量：在 `video:canplay` 后恢复；并移除“仅 WebKit 才恢复倍速”的限制（Chrome 也恢复）
  - 暂停状态：切源前记住 paused，切源后保持 paused/playing 不变
- **修复刷新后“显示第 N 集但实际解析/播放第 1 集”的竞态**：
  - 症状：`initAll` 早期用 `episodeIndex=0` 调了 `updateVideoUrl`，随后 `isInitializingRef=true` 导致正确的 `updateVideoUrl` 被跳过且不会重跑
  - 修复：初始化中跳过 `updateVideoUrl` 时记录 pending，初始化结束后补跑一次；并在 `initAll` 的本地资源分支优先使用 `currentEpisodeIndexRef.current`（避免 state 未就绪）

#### 怀疑点 B2：`isM3u8LikeUrl(videoUrl)` 误判导致未走 `customType.m3u8`

如果 `artOptions.type` 没被设为 `m3u8`，Artplayer 可能不会走 `customType.m3u8`，从而不创建 Hls 实例。

验证动作：

- 打印 `videoUrl` 与 `isM3u8LikeUrl(videoUrl)` 结果（临时日志）
- 确认命中本地时 `videoUrl` 形态是 `/api/local-video?...type=m3u8`（应被判定为 m3u8-like）

#### 怀疑点 B3：状态恢复逻辑与“历史记录为准”不一致

目前播放器恢复进度依赖 `resumeTimeRef`，而你要求“以历史记录为准”：

修订建议（行为定义）：

- 切源触发时：
  - 从历史记录读取 `play_time` 作为目标时间（如果没有记录再 fallback 到当前 `currentTime`）
  - 同时保存并恢复：
    - 音量：`lastVolumeRef`
    - 倍速：`lastPlaybackRateRef`（注意：现有逻辑有 `isWebkit` 限制，需去掉以满足 Chrome）
    - 暂停状态：切源前是否 paused（切源后应保持 paused，不要强制 autoplay）

### 3.3 建议的“最小可行修订”实施顺序（MVP）

1. **先修切源黑屏（稳定性优先）**
   - 非 WebKit 的 `switchUrl` 分支：切源前 `destroy old hls`
   - 切源后等待 `video:canplay` 再解除 loading
2. **再做状态保留（体验）**
   - 倍速/音量/暂停 + 历史记录进度恢复
3. **最后补埋点与回归用开关**
   - 例如 `NEXT_PUBLIC_PLAYER_DEBUG=1` 时打印关键链路日志（仅开发环境）
