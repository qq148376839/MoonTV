## 1. 实施概述

本次开发完成了"官方与非官方资源搜索独立"功能，实现了官方资源和非官方资源的独立搜索接口集成，并更新了播放流程以使用新的解析 API。

### 当前状态总结

**✅ 已完成**：

- 搜索功能独立化（官方和非官方资源分离）
- SSR 错误修复
- SSE 流式返回修复（真正的流式返回，每个源完成后立即推送）
- Worker 搜索源优化（添加缺失源、增加超时时间、详细日志）
- 内网地址自动检测和转换逻辑（后端+前端）
- Origin 获取逻辑优化（避免 `0.0.0.0` 问题）
- 代理 API 错误处理改进

**⚠️ 待解决**：

- **代理 API 无法访问内网地址**：直接访问内网地址可以正常播放，但通过代理 API 访问时失败
  - 问题：`fetch failed` 或网络连接错误
  - 影响：官方资源解析后的内网地址无法通过代理播放
  - 需要：排查 Next.js Node.js runtime 的网络访问限制，或使用替代方案

## 2. 核心功能实现

### 2.1 搜索功能独立化

**实现位置**：`src/lib/search-independent.ts`

**功能说明**：

- `searchOfficialResources()`：从官方资源搜索接口获取搜索结果
- `searchUnofficialResources()`：从非官方资源搜索接口获取搜索结果
- 两个函数都支持 SSE 格式和 JSON 格式响应
- 自动处理官方和非官方资源的不同数据格式

**环境变量配置**：

- `NEXT_PUBLIC_OFFICIAL_SEARCH_URL`：官方资源搜索接口（默认：`https://789jx.riowang.win`）
- `NEXT_PUBLIC_UNOFFICIAL_SEARCH_URL`：非官方资源搜索接口（默认：`https://ss.riowang.win`）

### 2.2 搜索流式 API 更新

**实现位置**：`src/app/api/search/stream/route.ts`

**重要变更**：

- ✅ **已移除**：config.json 中搜索源的调用（`searchTasks`）
- ✅ **仅使用**：官方和非官方资源搜索接口
- ✅ **简化代码**：移除了 `AdaptiveTimeoutManager`、`searchFromApiWithTimeout` 等不再需要的代码
- ✅ **流式返回优化**（2025-02-01）：
  - 如果配置了 `NEXT_PUBLIC_CF_SEARCH_WORKER_URL`，直接转发 Worker 的流式数据
  - 如果没有配置 Worker URL，直接调用官方和非官方资源搜索接口，并使用 `response.body.getReader()` 流式处理 SSE 响应
  - 每个源完成后立即推送结果，而不是等待所有源完成
  - 修复了消息格式，将 `source` 和 `source_name` 放在顶层

**代码变更**：

```typescript
// 修改前：
Promise.allSettled([officialSearchTask, unofficialSearchTask, ...searchTasks]);

// 修改后：

// 流式处理优化（2025-02-01）：
// 使用 response.body.getReader() 流式处理 SSE 响应
// 每个源完成后立即推送结果
```

### 2.3 播放流程更新

### ✅ 问题 4：SSE 流式返回问题（已修复，2025-02-01）

**问题描述**：

- 虽然使用了 SSE（Server-Sent Events），但前端感觉还是等待所有源完成后才统一返回结果
- 实际上应该是每个源完成后立即返回，而不是等待所有源完成
- 前端日志显示只收到一次结果消息，而不是多次流式消息

**根本原因**：

- `searchOfficialResources` 和 `searchUnofficialResources` 函数使用 `await response.text()` 等待整个响应完成
- 本地 API 等待这两个函数完成后才推送结果，导致不是真正的流式返回

**修复内容**：

1. ✅ **Worker 转发**：如果配置了 `NEXT_PUBLIC_CF_SEARCH_WORKER_URL`，直接转发 Worker 的流式数据
2. ✅ **流式处理 SSE**：如果没有配置 Worker URL，直接调用官方和非官方资源搜索接口，并使用 `response.body.getReader()` 流式处理 SSE 响应
3. ✅ **消息格式修复**：将 `source` 和 `source_name` 放在消息顶层，方便前端解析
4. ✅ **前端日志优化**：添加了详细的 SSE 日志，记录每个收到的消息和解析后的数据

**修复后的效果**：

- 每个源完成后立即推送结果，前端立即更新 UI
- 用户可以看到结果逐步返回，而不是等待所有源完成
- 前端日志显示多个 `[SSE] 📥 收到 X 个结果` 的消息

### ⚠️ 问题 5：CORS 跨域问题（部分解决，代理 API 访问内网地址仍有问题）

**问题描述**：

- 解析 API 返回的 m3u8_url 是内网地址（如 `http://192.168.31.18:1233/api/v1/m3u8/...`）
- 浏览器直接访问这些 URL 时被 CORS 策略阻止
- 错误信息：`Access to video at 'http://192.168.31.18:1233/api/v1/m3u8/...' from origin 'http://localhost:51000' has been blocked by CORS policy`
- **核心矛盾**：如果解析项目返回公网地址（如 `gfjx.riowang.win`），虽然能解决 CORS，但会浪费网络资源（因为实际都在本地 NAS 上）

**解决方案**：
在 `/api/parse/route.ts` 中自动检测内网地址并转换为代理 URL：

1. ✅ 解析项目可以继续返回内网地址（如 `http://192.168.31.18:1233/api/v1/m3u8/...`），不浪费网络资源
2. ✅ `/api/parse` 自动检测内网地址模式（192.168.x.x、10.x.x.x、172.16-31.x.x、localhost 等）
3. ✅ 如果是内网地址，自动转换为代理 URL（`/api/proxy/m3u8?url=...`）返回给前端
4. ✅ 前端使用代理 URL，不会有 CORS 问题
5. ✅ 代理 API 在服务器端访问内网地址，也不会有 CORS 问题

**已实施的修复**：

1. ✅ **后端**：修改 `/api/parse/route.ts`，添加内网地址检测和自动转换逻辑
2. ✅ **前端**：优化播放器逻辑，添加内网地址检测函数和代理 URL 转换函数
3. ✅ **前端**：播放器自动检测内网地址和外部 URL，统一通过代理访问
4. ✅ **代理 API**：修改代理 API，自动转换 m3u8 文件中的 TS 片段 URL 为代理 URL
5. ✅ **代理 API**：添加 TS 片段文件支持（二进制数据）
6. ✅ **代理 API**：修复 origin 获取逻辑，避免使用 `0.0.0.0` 等无效地址
7. ✅ **代理 API**：将 runtime 从 `edge` 改为 `nodejs`，以便访问内网地址
8. ✅ **代理 API**：改进错误处理，提供更详细的错误信息

**已解决的问题**：

- ✅ **代理 API 无法访问内网地址**（已修复）：
  - **问题现象**：
    - 直接访问 `http://192.168.31.18:1233/api/v1/m3u8/4ce095b2a534a435` 可以正常播放 ✅
    - 通过代理 API `/api/proxy/m3u8?url=http://192.168.31.18:1233/api/v1/m3u8/...` 访问时失败 ❌
  - **错误信息**：
    ```
    Proxy error: Error: fetch failed
    GET /api/proxy/m3u8?url=http%3A%2F%2F192.168.31.18%3A1233%2Fapi%2Fv1%2Fm3u8%2F... 500
    ```
  - **根本原因**：
    - Node.js 的 `fetch` API 在某些环境下无法访问内网地址（可能是 DNS 解析、网络接口绑定等问题）
  - **解决方案**：
    1. ✅ 创建了 `src/lib/http-client.ts`，使用 Node.js 原生 `http`/`https` 模块替代 `fetch`
    2. ✅ 修改了 `/api/proxy/m3u8/route.ts`，使用新的 HTTP 客户端
    3. ✅ 改进了错误处理，提供更详细的网络错误信息（ECONNREFUSED, ENOTFOUND, ETIMEDOUT 等）
    4. ✅ 添加了超时控制（30 秒）
    5. ✅ 优化了 IP 地址处理，避免 DNS 解析问题
  - **技术细节**：
    - 使用 `http.request()` 和 `https.request()` 替代 `fetch()`
    - 支持二进制数据（TS 文件）和文本数据（M3U8 文件）
    - 自动检测协议（http/https）
    - 正确处理内网 IP 地址，避免 DNS 解析
  - **相关文档**：
    - 详细的问题分析和解决方案文档：`docs/features/250201-代理API访问内网地址问题分析与解决方案.md`

**技术细节**：

**后端实现（`/api/parse/route.ts`）**：

- 内网地址检测模式：
  - `localhost`、`127.0.0.1`
  - `192.168.x.x`
  - `10.x.x.x`
  - `172.16.x.x` - `172.31.x.x`
  - `169.254.x.x`（链路本地地址）
- Origin 获取逻辑（避免使用 `0.0.0.0` 等无效地址）：
  1. 优先使用 `Origin` 请求头
  2. 如果没有，使用 `Host` 头 + 协议构建 origin
  3. 最后才使用 `request.url` 的 origin，如果包含 `0.0.0.0` 则替换为 `localhost`
- 转换逻辑：`${origin}/api/proxy/m3u8?url=${encodeURIComponent(originalUrl)}`

**前端实现（`src/app/play/page.tsx`）**：

- 添加 `isPrivateIP()` 函数：检测 URL 是否是内网地址
- 添加 `convertToProxyUrlIfNeeded()` 函数：统一处理 URL 转换逻辑
- 代理规则：
  1. 如果 URL 已经是代理 URL（`/api/proxy/m3u8`开头），直接使用
  2. 如果 URL 是本地 API 路径（`/api/`开头），直接使用
  3. 如果是内网地址，转换为代理 URL
  4. 如果是外部 URL，转换为代理 URL
  5. 非官方资源 + 去广告开关开启 → 代理时清理广告
  6. 官方资源 → 代理时不去广告（仅解决 CORS 问题）

**代理 API 实现（`/api/proxy/m3u8/route.ts`）**：

- **Runtime 配置**：使用 `nodejs` runtime（而非 `edge`），以便访问内网地址
- 自动转换 m3u8 文件中的 TS 片段 URL 为代理 URL
- Origin 获取逻辑（与 `/api/parse` 相同，避免使用 `0.0.0.0` 等无效地址）：
  1. 优先使用 `Origin` 请求头
  2. 如果没有，使用 `Host` 头 + 协议构建 origin
  3. 最后才使用 `request.nextUrl.origin`，如果包含 `0.0.0.0` 则替换为 `localhost`
- TS 片段文件支持（二进制数据）
- **错误处理**：改进错误处理，提供更详细的错误信息，区分网络错误和其他错误

**双重保障**：

- 后端 `/api/parse` 会自动转换内网地址为代理 URL
- 前端播放器也会检测并转换内网地址和外部 URL
- 即使后端没有转换，前端也能正确处理

## 6. 测试建议

### CORS 问题排查清单

如果遇到 CORS 错误，请检查：

1. **播放器日志**：

   - `[Player] 使用代理解决CORS问题:` - 确认是否使用了代理
   - `[Player] HLS加载源:` - 确认加载的 URL 是否是代理 URL

2. **网络请求**：

   - 检查浏览器 Network 面板，确认 m3u8 文件是否通过 `/api/proxy/m3u8` 加载
   - 检查 m3u8 文件内容，确认 TS 片段 URL 是否已转换为代理 URL

3. **代理 API 日志**：

   - 检查服务器日志，确认代理 API 是否被调用
   - 确认代理 API 是否正确处理了 TS 片段请求
   - **重要**：检查是否有 `fetch failed` 或网络连接错误

4. **HLS.js 配置**：
   - 确认 HLS.js 是否正确使用了代理 URL
   - 检查是否有自定义 loader 覆盖了代理逻辑

### 代理 API 访问内网地址问题排查

如果代理 API 无法访问内网地址，请检查：

1. **直接访问测试**：

   - 在服务器上直接访问内网地址：`curl http://192.168.31.18:1233/api/v1/m3u8/...`
   - 确认服务器可以访问内网地址

2. **Next.js 进程网络访问**：

   - 检查 Next.js 进程是否有权限访问内网地址
   - 检查防火墙规则，确保 Next.js 进程可以访问内网
   - 检查网络配置，确保服务器可以访问内网地址

3. **代理 API 日志**：

   - 查看服务器日志中的详细错误信息
   - 检查错误类型：`fetch failed`、`ECONNREFUSED`、`ENOTFOUND` 等
   - 确认错误发生在哪个步骤（fetch 请求、响应处理等）

4. **可能的解决方案**：
   - 尝试使用 Node.js 的 `http`/`https` 模块替代 `fetch` API
   - 检查是否需要配置代理服务器
   - 验证服务器网络配置
