## 1. 背景与目标

### 1.1 业务背景

在高峰期，很多影片资源会因为访问量过高导致实际播放特别卡顿，影响用户体验。用户希望能够将热门资源下载到本地，实现流畅播放。

### 1.2 用户痛点

- **高峰期播放卡顿**：热门资源在高峰期访问量过大，导致播放卡顿、缓冲时间长
- **网络不稳定**：部分用户网络环境不稳定，在线播放体验差
- **重复观看成本高**：用户重复观看同一资源时，每次都需要重新加载，浪费带宽和时间
- **OrionTV 兼容性**：需要支持 OrionTV 等第三方客户端也能触发下载功能

### 1.3 业务目标

- **主要目标**：
  - 提升高峰期播放流畅度，减少卡顿率 80% 以上
  - 支持本地资源播放，降低网络依赖
  - 实现资源自动下载和管理
- **成功指标**：
  - 本地资源播放成功率 ≥ 95%
  - 下载任务成功率 ≥ 90%
  - 用户对播放流畅度满意度 ≥ 4.5/5.0
  - OrionTV 客户端下载触发成功率 ≥ 90%

### 1.4 项目范围

- **包含范围**：
  - 资源下载功能（手动下载、自动下载）
  - 本地资源存储和管理
  - 资源刮削和元数据生成
  - 本地资源播放功能
  - Docker 部署数据持久化
  - OrionTV 兼容的下载 API
- **不包含范围**：
  - 资源分享功能（后续迭代）
  - 下载队列管理界面（后续迭代）
  - 资源清理和空间管理（后续迭代）

## 2. 用户与场景

### 2.1 目标用户

- **主要用户**：经常观看影视内容的用户
- **用户特征**：
  - 对播放流畅度要求高
  - 有本地存储空间（NAS、服务器等）
  - 经常重复观看同一资源

### 2.2 使用场景

**场景 1：手动下载资源**

- **用户**：普通用户
- **时间**：观看前或观看时
- **地点**：任意地点
- **行为**：点击"下载"按钮，选择要下载的资源
- **目标**：将资源下载到本地，后续可以流畅播放

**场景 2：自动下载播放记录中的资源**

- **用户**：经常观看的用户
- **时间**：播放记录生成后
- **地点**：服务器端
- **行为**：系统自动检测播放记录，后台下载资源
- **目标**：确保用户下次观看时资源已下载完成

**场景 3：OrionTV 触发下载**

- **用户**：使用 OrionTV 客户端的用户
- **时间**：通过 OrionTV 播放时
- **地点**：服务器端
- **行为**：OrionTV 调用下载 API，触发资源下载
- **目标**：第三方客户端也能使用下载功能

**场景 4：本地资源播放**

- **用户**：已下载资源的用户
- **时间**：观看时
- **地点**：任意地点
- **行为**：系统检测到本地有资源，优先使用本地资源播放
- **目标**：流畅播放，无卡顿

### 2.3 用户故事

- As a 用户, I want 下载资源到本地, So that 我可以在高峰期流畅播放
- As a 用户, I want 播放记录中的资源自动下载, So that 我下次观看时无需等待
- As a OrionTV 用户, I want 通过 API 触发下载, So that 我可以在客户端使用下载功能
- As a 用户, I want 系统自动使用本地资源播放, So that 我无需手动选择

### 3.2 功能详细说明

#### 功能 1：手动下载功能

**优先级**：P0

**功能描述**：
用户可以在播放页面或详情页点击"下载"按钮，手动触发资源下载。

**交互流程**：

1. 用户点击"下载"按钮
2. 系统检查资源是否已下载
3. 如果未下载，显示下载确认对话框
4. 用户确认后，开始下载
5. 显示下载进度
6. 下载完成后，更新资源状态

**输入输出**：

- **输入**：资源信息（source、id、episodes）
- **输出**：下载任务 ID、下载进度、下载状态

**边界条件**：

- 资源已下载：提示"资源已存在，无需重复下载"
- 存储空间不足：提示"存储空间不足，请清理后重试"
- 下载失败：提示"下载失败，请检查网络后重试"
- 资源 URL 无效：提示"资源地址无效，无法下载"

**验收标准**：

- [ ] 可以点击下载按钮触发下载
- [ ] 下载过程中显示进度
- [ ] 下载完成后资源可以播放
- [ ] 下载失败时显示错误信息

#### 功能 2：自动下载功能

**优先级**：P0

**功能描述**：
播放记录中的资源自动下载到本地，无需用户手动操作。

**交互流程**：

1. 用户播放资源，生成播放记录
2. 系统检测到新的播放记录
3. 检查资源是否已下载
4. 如果未下载，后台自动开始下载
5. 下载完成后，更新资源状态

**输入输出**：

- **输入**：播放记录（source、id、episodes）
- **输出**：下载任务状态

**边界条件**：

- 播放记录已存在资源：跳过下载
- 存储空间不足：记录日志，不下载
- 下载失败：记录日志，可重试
- 资源 URL 无效：跳过下载

**验收标准**：

- [ ] 播放记录生成后自动触发下载
- [ ] 下载在后台进行，不影响用户操作
- [ ] 下载完成后资源可以播放
- [ ] 下载失败时记录日志

#### 功能 3：资源刮削功能

**优先级**：P0

**功能描述**：
下载资源时，自动生成资源元数据 JSON 文件，包含资源信息、集数、播放地址等，便于管理和播放。

**交互流程**：

1. 资源下载完成
2. 系统提取资源元数据（标题、年份、集数、封面等）
3. 生成 JSON 文件，格式与现有资源格式一致
4. 保存 JSON 文件到资源目录

**输入输出**：

- **输入**：资源信息（SearchResult）
- **输出**：JSON 文件（包含资源元数据）

**JSON 格式示例**：

```json
{
  "id": "local_12345",
  "title": "影片标题",
  "poster": "封面地址",
  "episodes": ["本地文件路径1", "本地文件路径2"],
  "source": "local",
  "source_name": "本地资源",
  "year": "2024",
  "desc": "剧情简介",
  "type_name": "电影",
  "local_path": "/data/videos/影片标题_2024",
  "original_source": "dyttzy",
  "original_id": "12345",
  "download_time": 1706342400000,
  "file_size": 2147483648,
  "episode_count": 1,
  "episodes_info": [
    {
      "index": 1,
      "file_path": "/data/videos/影片标题_2024/第1集.mp4",
      "file_size": 2147483648,
      "duration": 5400,
      "resolution": "1080p"
    }
  ]
}
```

**边界条件**：

- 资源信息不完整：使用默认值填充缺失字段
- JSON 文件生成失败：记录日志，不影响下载
- 文件路径冲突：自动重命名，避免覆盖

**验收标准**：

- [ ] 下载完成后自动生成 JSON 文件
- [ ] JSON 格式与现有资源格式兼容
- [ ] JSON 文件包含完整的资源元数据
- [ ] JSON 文件可以用于资源搜索和播放

#### 功能 4：本地资源播放

**优先级**：P0

**功能描述**：
系统检测到本地有资源时，优先使用本地资源播放，提升播放流畅度。

**交互流程**：

1. 用户点击播放
2. 系统检查本地是否有该资源
3. 如果本地有资源，使用本地资源播放
4. 如果本地无资源，使用在线资源播放
5. 显示资源来源标识（本地/在线）

**输入输出**：

- **输入**：资源标识（source、id）
- **输出**：播放地址（本地路径或在线 URL）

**边界条件**：

- 本地资源不存在：回退到在线播放
- 本地资源损坏：回退到在线播放，记录日志
- 本地资源不完整：使用已下载部分，缺失部分在线播放
- 权限不足：提示权限错误，回退到在线播放

**验收标准**：

- [ ] 本地有资源时优先使用本地资源
- [ ] 本地资源播放流畅，无卡顿
- [ ] 本地资源不存在时自动回退到在线播放
- [ ] 显示资源来源标识

#### 功能 5：Docker 数据持久化

**优先级**：P0

**功能描述**：
支持 Docker 部署时，通过 Volume 挂载实现数据持久化，确保重新部署时已下载的数据不丢失。

**实现方案**：

1. 使用 Docker Volume 挂载本地存储目录
2. 配置环境变量指定存储路径
3. 启动时检查存储目录，确保可写
4. 支持自定义存储路径

**Docker Compose 配置示例**：

```yaml
services:
  moontv:
    image: ghcr.io/senshinya/moontv:latest
    container_name: moontv
    restart: unless-stopped
    ports:
      - '3000:3000'
    environment:
      - PASSWORD=your_password
      - LOCAL_STORAGE_PATH=/data/videos
    volumes:
      - ./data/videos:/data/videos
      - ./config.json:/app/config.json:ro
```

**环境变量配置**：

- `LOCAL_STORAGE_PATH`：本地存储路径（默认：`/data/videos`）
- `LOCAL_STORAGE_ENABLED`：是否启用本地存储（默认：`true`）

**边界条件**：

- Volume 未挂载：提示错误，禁用下载功能
- 存储路径不可写：提示错误，禁用下载功能
- 存储空间不足：提示警告，限制下载

**验收标准**：

- [ ] Docker 部署时支持 Volume 挂载
- [ ] 重新部署后数据不丢失
- [ ] 支持自定义存储路径
- [ ] 存储路径不可用时提示错误

#### 功能 6：多站点资源分割

**优先级**：P1

**功能描述**：
同一资源来自不同站点时，分别下载并存储为不同的视频文件，支持多源选择。

**交互流程**：

1. 检测到同一资源有多个站点来源
2. 为每个站点创建独立的存储目录
3. 分别下载各站点的资源
4. 生成独立的 JSON 元数据
5. 在播放时支持选择不同站点的资源

**存储结构示例**：

```
/data/videos/
  ├── 影片标题_2024/
  │   ├── dyttzy/          # 电影天堂资源
  │   │   ├── metadata.json
  │   │   └── 第1集.mp4
  │   ├── heimuer/        # 黑木耳资源
  │   │   ├── metadata.json
  │   │   └── 第1集.mp4
  │   └── ruyi/           # 如意资源
  │       ├── metadata.json
  │       └── 第1集.mp4
```

**输入输出**：

- **输入**：资源信息（多个站点的 source、id、episodes）
- **输出**：多个站点的本地资源文件

**边界条件**：

- 同一站点资源已存在：跳过下载
- 部分站点下载失败：其他站点继续下载
- 存储空间不足：优先下载优先级高的站点

**验收标准**：

- [ ] 同一资源不同站点分别存储
- [ ] 每个站点有独立的元数据文件
- [ ] 播放时可以选择不同站点的资源
- [ ] 部分站点下载失败不影响其他站点

#### 功能 7：OrionTV 下载 API

**优先级**：P0

**功能描述**：
提供 API 接口，支持 OrionTV 等第三方客户端触发资源下载功能。

**API 接口设计**：

```
POST /api/download
Content-Type: application/json

Request:
{
  "source": "dyttzy",
  "id": "12345",
  "episodes": ["http://example.com/ep1.m3u8"],
  "auto_download": true  // 是否自动下载所有集数
}

Response:
{
  "success": true,
  "task_id": "download_1234567890",
  "status": "queued",
  "message": "下载任务已创建"
}
```

**交互流程**：

1. OrionTV 客户端调用下载 API
2. 系统验证请求参数
3. 创建下载任务
4. 返回任务 ID 和状态
5. 后台执行下载任务

**输入输出**：

- **输入**：资源信息（source、id、episodes）
- **输出**：下载任务 ID、任务状态

**边界条件**：

- 参数无效：返回 400 错误
- 资源已下载：返回已存在状态
- 存储空间不足：返回 507 错误
- 下载任务创建失败：返回 500 错误

**验收标准**：

- [ ] OrionTV 可以调用 API 触发下载
- [ ] API 返回正确的任务状态
- [ ] 下载任务可以正常执行
- [ ] API 错误处理正确

## 4. 非功能需求

### 4.1 性能要求

- **下载速度**：支持多线程下载，充分利用带宽
- **下载并发**：支持同时下载多个资源（默认最多 3 个）
- **存储空间**：支持大文件存储（单个文件最大支持 100GB）
- **响应时间**：资源检查响应时间 ≤ 100ms
- **播放延迟**：本地资源播放延迟 ≤ 500ms

### 4.2 安全要求

- **文件权限**：下载的文件仅服务器可访问，不对外暴露
- **路径安全**：防止路径遍历攻击
- **存储隔离**：不同用户的资源隔离存储（如需要）
- **资源验证**：下载前验证资源 URL 有效性

### 4.3 兼容性要求

- **文件格式**：支持 MP4、M3U8、MKV 等常见视频格式
- **存储系统**：支持本地文件系统、NAS 挂载
- **Docker 环境**：支持 Docker 和 Docker Compose 部署
- **操作系统**：支持 Linux、macOS、Windows（服务器端）

#### 4.3.1 视频格式处理说明

**格式来源**：

- 下载后的文件格式**取决于原始播放源的格式**
- 实际采集的资源主要为 **M3U8 格式**（HLS 流媒体）
- 部分资源可能为 MP4、MKV 等直接文件格式

**M3U8 格式处理方案**：

**方案 1：直接保存 M3U8 文件（推荐，MVP 版本）**

- **实现方式**：

  - 下载 M3U8 播放列表文件（`.m3u8`）
  - 解析 M3U8 内容，下载所有 TS 片段文件（`.ts`）
  - 保存 M3U8 文件和 TS 片段到本地
  - 播放时使用本地 M3U8 文件，通过 HTTP 服务提供访问

- **优点**：

  - 实现简单，无需格式转换
  - 下载速度快，支持断点续传
  - 保持原始质量，无转码损失
  - 支持 HLS 播放器的标准功能（拖拽、多码率等）

- **缺点**：

  - 文件数量多（M3U8 + 多个 TS 片段）
  - 存储结构相对复杂
  - 需要维护 M3U8 文件中的相对路径

- **存储结构示例**：
  ```
  /data/videos/影片标题_2024/dyttzy_12345/
  ├── episode_01.m3u8          # M3U8 播放列表
  ├── episode_01/
  │   ├── segment_000.ts       # TS 片段
  │   ├── segment_001.ts
  │   └── ...
  └── metadata.json
  ```

**方案 2：转换为 MP4 格式（后续优化版本）**

- **实现方式**：

  - 下载 M3U8 文件和 TS 片段
  - 使用 FFmpeg 等工具将 TS 片段合并为 MP4
  - 删除原始 TS 片段，节省存储空间
  - 保存为单个 MP4 文件

- **优点**：

  - 文件结构简单，单个文件
  - 兼容性更好，支持更多播放器
  - 存储空间可能更小（取决于编码）

- **缺点**：
  - 需要转码，消耗 CPU 资源
  - 转码时间长，影响下载速度
  - 可能损失画质（取决于转码参数）

**推荐方案**：

- **MVP 版本**：采用方案 1（直接保存 M3U8），快速实现，满足基本需求
- **后续优化**：提供选项，用户可选择是否转换为 MP4（可配置）

**文件格式识别**：

  - 如果 URL 以 `.m3u8` 结尾 → 按 M3U8 格式处理
  - 如果 URL 以 `.mp4`、`.mkv` 等结尾 → 按直接文件格式处理
  - 如果无法识别 → 尝试下载并检测 Content-Type

## 7. 方案对比分析

### 7.1 下载触发时机方案对比

#### 方案 A：点击下载按钮触发下载

**优点**：

- ✅ 用户主动控制，不会意外下载不需要的资源
- ✅ 减少服务器负载，避免无效下载
- ✅ 用户可以选择性下载，节省存储空间
- ✅ 下载行为明确，用户有预期

**缺点**：

- ❌ 需要用户手动操作，增加操作步骤
- ❌ 用户可能忘记下载，错过流畅播放机会
- ❌ 首次播放时仍需等待在线加载

**适用场景**：

- 用户明确知道要下载的资源
- 存储空间有限，需要选择性下载
- 用户希望完全控制下载行为

#### 方案 B：播放时自动触发下载

**优点**：

- ✅ 无需用户操作，自动化程度高
- ✅ 用户首次播放时即可开始下载，下次播放更流畅
- ✅ 符合"懒加载"理念，按需下载
- ✅ 提升用户体验，减少操作步骤

**缺点**：

- ❌ 可能下载用户不需要的资源（只看一次）
- ❌ 增加服务器负载，可能影响播放性能
- ❌ 用户可能不知道资源正在下载
- ❌ 存储空间消耗不可控

**适用场景**：

- 用户经常重复观看同一资源
- 存储空间充足
- 希望最大化自动化体验

#### 方案 C：混合方案（推荐）

**方案描述**：

- **手动下载**：提供"下载"按钮，用户可主动下载
- **播放时下载**：播放时延迟触发下载（播放 5 秒后开始），用户可关闭
- **播放记录自动下载**：播放记录中的资源自动下载（后台静默下载）

**优点**：

- ✅ 兼顾用户控制和自动化体验
- ✅ 播放记录自动下载确保常用资源已下载
- ✅ 播放时下载延迟触发，避免影响首次播放
- ✅ 用户可通过设置控制下载行为

**缺点**：

- ❌ 实现复杂度较高
- ❌ 需要管理多种下载触发场景

**推荐理由**：

1. **用户体验最佳**：既有自动化，又有控制权
2. **资源利用合理**：播放记录自动下载确保常用资源可用
3. **性能影响可控**：延迟触发避免影响首次播放
4. **灵活性高**：用户可根据需求调整设置

**实现建议**：

- 默认启用"播放记录自动下载"
- 默认启用"播放时延迟下载"（延迟 5 秒）
- 提供设置页面，用户可调整：
  - 是否启用播放时下载
  - 延迟下载时间（0-30 秒）
  - 是否启用播放记录自动下载
  - 最大并发下载数

## 8. 播放记录自动下载详细设计

### 8.1 功能概述

播放记录中的资源自动下载到本地，确保用户下次观看时资源已就绪。

### 8.2 触发时机

- **触发条件**：播放记录保存时（`/api/playrecords` POST 请求）
- **触发方式**：后台异步触发，不影响播放记录保存性能
- **下载范围**：当前播放的集数 + 可选的下 N 集（可配置）

### 8.3 数据提取逻辑

#### 问题分析

播放记录（PlayRecord）数据结构：

```typescript
interface PlayRecord {
  title: string;
  source_name: string; // 站点名称（如"电影天堂"）
  cover: string;
  year: string;
  index: number; // 当前集数
  total_episodes: number;
  play_time: number;
  total_time: number;
  save_time: number;
  search_title: string; // 搜索标题
}
```

**问题**：播放记录中没有 `source`（站点 key）和 `id`（资源 ID），无法直接下载。

#### 解决方案

**方案 1：播放记录保存时同时保存 source 和 id（推荐）**

- **实现方式**：

  1. 修改 `PlayRecord` 接口，增加 `source` 和 `id` 字段
  2. 保存播放记录时，同时保存 `source` 和 `id`
  3. 下载时直接从播放记录中获取

- **优点**：

  - 数据完整，无需额外查询
  - 下载逻辑简单直接
  - 性能最优

- **缺点**：
  - 需要修改数据结构（向后兼容）

**方案 2：通过 search_title 和 source_name 反向查找**

- **实现方式**：

  1. 使用 `search_title` 和 `source_name` 搜索资源
  2. 匹配到资源后获取 `source` 和 `id`
  3. 然后触发下载

- **优点**：

  - 不需要修改现有数据结构
  - 向后兼容

- **缺点**：
  - 需要额外的搜索请求，性能较差
  - 可能匹配失败（标题变化、站点名称变化）

**推荐方案**：采用方案 1，同时兼容方案 2 作为降级方案。

### 8.4 实现流程

```
1. 用户播放资源，触发播放记录保存
   ↓
2. API 接收播放记录数据（包含 source、id、episodes）
   ↓
3. 保存播放记录到数据库
   ↓
4. 后台异步触发下载任务
   ↓
5. 检查资源是否已下载
   ├─ 已下载 → 跳过
   └─ 未下载 → 继续
   ↓
6. 获取资源详情（episodes 列表）
   ↓
7. 创建下载任务（当前集数 + 下N集）
   ↓
8. 加入下载队列
   ↓
9. 后台执行下载
   ↓
10. 下载完成后更新资源状态
```

### 8.5 下载范围策略

**策略 1：仅下载当前集数**

- **优点**：节省存储空间，下载速度快
- **缺点**：用户连续观看时需要等待下载
- **适用场景**：存储空间有限，用户观看习惯不固定

**策略 2：下载当前集数 + 下 N 集（推荐）**

- **优点**：预下载后续集数，提升连续观看体验
- **缺点**：占用更多存储空间
- **实现方式**：
  - 默认下载当前集数 + 下 2 集
  - 用户可配置下载集数范围（0-10 集）
  - 电视剧自动下载更多集数，电影仅下载当前

**策略 3：下载全部集数**

- **优点**：一次性下载完成，后续无需等待
- **缺点**：占用大量存储空间，下载时间长
- **适用场景**：用户明确要完整观看，存储空间充足

**推荐策略**：采用策略 2，支持用户自定义配置。

### 8.6 OrionTV 兼容性

**问题**：OrionTV 等第三方客户端调用 `/api/playrecords` 保存播放记录时，也需要触发下载。

**解决方案**：

1. **统一触发机制**：无论来源（Web 端、OrionTV），保存播放记录时统一触发下载
2. **API 兼容**：确保 `/api/playrecords` POST 接口支持 `source` 和 `id` 参数
3. **降级处理**：如果没有 `source` 和 `id`，使用方案 2（反向查找）作为降级

**API 请求示例**：

```json
POST /api/playrecords
{
  "key": "dyttzy_12345",
  "title": "影片标题",
  "source": "dyttzy",        // 新增：站点key
  "id": "12345",             // 新增：资源ID
  "source_name": "电影天堂",
  "cover": "https://example.com/poster.jpg",
  "year": "2024",
  "index": 1,
  "total_episodes": 24,
  "play_time": 1200,
  "total_time": 3600,
  "search_title": "影片标题"
}
```

**实现要点**：

- 播放记录保存接口需要支持 `source` 和 `id` 参数（可选，向后兼容）
- 如果提供了 `source` 和 `id`，直接触发下载
- 如果没有提供，尝试通过 `search_title` 和 `source_name` 反向查找
- 下载任务异步执行，不阻塞播放记录保存

## 9. Docker 部署数据持久化详细设计

### 9.1 问题分析

**问题**：Docker 容器重新部署时，容器内的数据会丢失，已下载的资源需要持久化保存。

**影响**：

- 用户下载的资源在容器重启后丢失
- 需要重新下载，浪费时间和带宽
- 影响用户体验

### 9.2 解决方案

#### 方案：使用 Docker Volume 挂载

#### 方案：使用 Docker Volume 挂载

**实现方式**：

1. **Volume 挂载**：将本地存储目录挂载到容器内
2. **环境变量配置**：通过环境变量指定存储路径
3. **启动时检查**：容器启动时检查存储路径权限和可用性
4. **数据持久化**：所有下载的资源存储在挂载的 Volume 中

**Docker Compose 配置示例**：

```yaml
services:
  moontv:
    image: ghcr.io/senshinya/moontv:latest
    container_name: moontv
    restart: unless-stopped
    ports:
      - '3000:3000'
    environment:
      - PASSWORD=your_password
      - LOCAL_STORAGE_PATH=/data/videos
      - LOCAL_STORAGE_ENABLED=true
    volumes:
      # 挂载视频存储目录（数据持久化）
      - ./data/videos:/data/videos
      # 挂载配置文件（只读）
      - ./config.json:/app/config.json:ro
      # 可选：挂载日志目录
      - ./logs:/app/logs
```

```bash
docker run -d \
```

### 9.3 环境变量配置

**必需环境变量**：

- `LOCAL_STORAGE_PATH`：本地存储路径（默认：`/data/videos`）
  - 容器内路径，需要与 Volume 挂载路径一致
  - 示例：`/data/videos`

**可选环境变量**：

- `LOCAL_STORAGE_ENABLED`：是否启用本地存储（默认：`true`）
  - 设置为 `false` 时，禁用下载功能
  - 示例：`true` 或 `false`
- `LOCAL_STORAGE_MAX_SIZE`：最大存储空间（GB，默认：无限制）
  - 超过限制时停止下载新资源
  - 示例：`500`（500GB）
- `LOCAL_STORAGE_AUTO_CLEANUP`：是否自动清理（默认：`false`）
  - 启用后自动清理旧资源（后续迭代）
  - 示例：`true` 或 `false`

### 9.4 启动时检查

**检查项**：

1. **Volume 挂载检查**：

   - 检查 `LOCAL_STORAGE_PATH` 目录是否存在
   - 如果不存在，尝试创建目录
   - 如果创建失败，记录错误并禁用下载功能

2. **权限检查**：

   - 检查存储路径是否可写
   - 如果不可写，记录错误并禁用下载功能

3. **空间检查**：
   - 检查可用存储空间
   - 如果空间不足（< 1GB），记录警告

**错误处理**：

- Volume 未挂载：记录错误日志，禁用下载功能，不影响其他功能
- 权限不足：记录错误日志，禁用下载功能，提示用户检查权限
- 空间不足：记录警告日志，允许下载，但限制下载大小

## 10. 多站点资源分割详细设计

### 10.1 问题分析

**问题**：同一个资源可能来自多个不同的站点，每个站点的资源质量、格式可能不同，需要分别存储和管理。

**场景示例**：

- 资源 A 在"电影天堂"（dyttzy）有 1080p 版本
- 资源 A 在"黑木耳"（heimuer）有 720p 版本
- 资源 A 在"如意"（ruyi）有 4K 版本

**需求**：

- 每个站点的资源分别下载和存储
- 播放时可以选择不同站点的资源
- 资源元数据需要区分不同站点

### 10.2 存储结构设计

#### 目录结构

```
/data/videos/
├── 影片标题_2024/                    # 资源根目录（按标题+年份）
│   ├── metadata.json                 # 资源总元数据（包含所有站点信息）
│   ├── dyttzy_12345/                # 电影天堂站点资源
│   │   ├── metadata.json            # 站点专属元数据
│   │   ├── episode_01.mp4           # 第1集
│   │   ├── episode_02.mp4           # 第2集
│   │   └── ...

│   │   ├── metadata.json
│   │   ├── episode_01.mp4
│   │   └── ...
│   └── ruyi_11111/                  # 如意站点资源
│       ├── metadata.json
│       ├── episode_01.mp4
```

**目录命名规则**：

- 资源根目录：`{title}_{year}`（标题\_年份，去除特殊字符）
- 站点子目录：`{source}_{id}`（站点 key\_资源 ID）

### 10.3 下载逻辑设计

#### 下载触发

1. **同一资源多个站点**：检测到同一资源有多个站点来源时，为每个站点创建独立的下载任务
2. **下载任务管理**：每个站点的下载任务独立管理，互不影响
3. **下载状态跟踪**：分别跟踪每个站点的下载状态（等待中/下载中/已完成/失败）

#### 下载流程

```
1. 检测到资源有多个站点来源
   ↓
2. 为每个站点创建独立的下载任务
   ↓
3. 并行或串行下载（根据配置）
   ↓
4. 每个站点下载完成后，生成独立的元数据文件
   ↓
5. 更新资源总元数据（metadata.json）
```

#### 下载策略

- **并行下载**：多个站点同时下载（默认最多 3 个并发）
- **串行下载**：按优先级顺序下载（可配置）
- **智能选择**：根据存储空间和网络情况，选择最优站点优先下载

### 10.4 播放选择逻辑

#### 资源检测

1. **检测本地资源**：播放时检测本地是否有该资源
2. **多站点匹配**：如果本地有多个站点的资源，返回所有可用站点
3. **站点选择**：用户可以选择使用哪个站点的资源播放

#### 播放流程

```
1. 用户请求播放资源（source、id）
   ↓
2. 系统检测本地是否有该资源
   ↓
3. 如果本地有多个站点版本：
   - 返回所有可用站点列表
   - 用户选择要播放的站点
   ↓
4. 如果本地只有一个站点版本：
   - 直接使用该站点资源
   ↓
5. 如果本地没有资源：
   - 回退到在线播放
```

```
    }
```

### 10.5 边界条件处理

**场景 1：部分站点下载失败**

- **处理方式**：其他站点继续下载，失败的站点记录日志
- **用户影响**：可以播放已成功下载的站点资源

**场景 2：同一站点重复下载**

- **处理方式**：检测到已存在时跳过下载，更新元数据
- **用户影响**：避免重复下载，节省存储空间

**场景 3：存储空间不足**

- **处理方式**：按优先级选择站点下载，低优先级站点暂停
- **用户影响**：优先保证重要资源下载

**场景 4：站点资源 URL 失效**

- **处理方式**：记录失败日志，其他站点继续下载
- **用户影响**：可以使用其他站点的资源

### 10.6 验收标准

- [ ] 同一资源多个站点可以分别下载
- [ ] 每个站点有独立的存储目录和元数据
- [ ] 播放时可以选择不同站点的资源
- [ ] 部分站点下载失败不影响其他站点
- [ ] 资源总元数据正确记录所有站点信息
- [ ] 站点专属元数据格式正确，可用于播放

## 11. 资源刮削详细设计

### 11.1 功能概述

资源刮削是指从原始资源信息中提取并生成标准化的元数据 JSON 文件，使本地资源能够像在线资源一样被搜索、管理和播放。

### 11.2 刮削时机

- **下载完成后**：资源下载完成后立即进行刮削
- **元数据更新**：资源信息变化时更新元数据
- **手动触发**：用户可手动触发重新刮削

### 11.3 元数据来源

1. **原始资源信息**：从 `SearchResult` 中提取
2. **文件系统信息**：从下载的文件中提取（大小、时长等）
3. **用户补充信息**：用户可手动补充缺失信息

### 11.4 元数据字段映射

| 原始字段    | 元数据字段        | 说明                    |
| ----------- | ----------------- | ----------------------- |
| `title`     | `title`           | 资源标题                |
| `year`      | `year`            | 年份                    |
| `poster`    | `poster`          | 封面地址                |
| `desc`      | `desc`            | 剧情简介                |
| `type_name` | `type_name`       | 类型（电影/电视剧）     |
| `source`    | `original_source` | 原始站点 key            |
| `id`        | `original_id`     | 原始资源 ID             |
| `episodes`  | `episodes`        | 本地文件路径数组        |
| -           | `source`          | 固定为 "local"          |
| -           | `source_name`     | "本地资源-{原始站点名}" |
| -           | `local_path`      | 本地存储路径            |
| -           | `download_time`   | 下载时间戳              |
| -           | `file_size`       | 文件总大小              |
| -           | `episode_count`   | 集数                    |
| -           | `episodes_info`   | 每集详细信息            |

### 11.5 文件命名规范

#### 资源目录命名

```
{title}_{year}
```

- 示例：`流浪地球_2019`
- 特殊字符处理：替换为下划线

#### 站点目录命名

```
{source}_{id}
```

- 示例：`dyttzy_12345`
- 保证唯一性

#### 视频文件命名

```
episode_{index}.{ext}
```

- 示例：`episode_01.mp4`、`episode_02.mkv`
- 索引从 01 开始，补齐两位

### 11.6 元数据生成流程

```
1. 资源下载完成
   ↓
2. 提取原始资源信息（SearchResult）
   ↓
3. 扫描下载的文件，获取文件信息
   ↓
4. 生成站点专属元数据（{source}_{id}/metadata.json）
   ↓
5. 更新资源总元数据（metadata.json）
   ↓
6. 更新资源索引（index.json）
```

### 11.7 验收标准

- [ ] 下载完成后自动生成元数据 JSON 文件
- [ ] 元数据格式与现有资源格式兼容
- [ ] 元数据包含完整的资源信息
- [ ] 元数据可用于资源搜索和播放
- [ ] 文件命名规范统一
- [ ] 多站点资源元数据正确区分

## 12. 本地资源播放详细设计

### 12.1 播放优先级策略

#### 优先级顺序

1. **本地资源**（最高优先级）
2. **在线资源**（降级方案）

#### 检测逻辑

```
1. 用户请求播放资源（source、id）
   ↓
2. 检查本地是否有该资源
   - 检查资源总元数据（metadata.json）
   - 检查站点专属元数据（{source}_{id}/metadata.json）
   ↓
3. 如果本地有资源：
   - 返回本地文件路径
   - 转换为HTTP服务地址（/api/local-video?path=...）
   ↓
4. 如果本地没有资源：
   - 返回在线资源URL
```

#### 本地资源匹配刷新机制

**刷新时机**：

1. **播放前检测**（实时检测）：

   - 用户点击播放时，立即检测本地资源
   - 检查资源索引文件（`index.json`）和元数据文件（`metadata.json`）
   - 验证文件实际存在性（避免元数据与文件系统不一致）

2. **下载完成后刷新**：

   - 资源下载完成时，立即更新资源索引（`index.json`）
   - 生成/更新元数据文件（`metadata.json`）
   - 触发资源索引缓存刷新（如果使用缓存）

3. **定时刷新**（可选，后台任务）：

   - 每 30 分钟扫描一次本地存储目录
   - 更新资源索引，同步文件系统状态
   - 清理已删除资源的元数据记录

4. **启动时刷新**：
   - 服务启动时，扫描本地存储目录
   - 重建资源索引（`index.json`）
   - 验证元数据与文件系统的一致性

**缓存更新策略**：

- **已播放的缓存记录**：**需要更新**

  - 当检测到本地资源时，更新播放记录中的资源来源标识（`source: "local"`）
  - 更新播放地址缓存，将在线 URL 替换为本地路径
  - 下次播放同一资源时，直接使用本地资源，无需重新检测

- **资源索引缓存**：

  - 使用内存缓存存储资源索引（`index.json`）
  - 下载完成时立即更新缓存
  - 定时刷新时同步更新缓存
  - 缓存失效时间：5 分钟（可配置）

- **元数据缓存**：
  - 每个资源的元数据文件（`metadata.json`）可以缓存
  - 文件修改时间变化时，自动刷新缓存
  - 缓存失效时间：10 分钟（可配置）

**实现要点**：

- 资源检测采用"元数据优先 + 文件验证"策略
- 先检查索引文件，快速判断资源是否存在
- 再验证实际文件是否存在，避免元数据与文件系统不一致
- 使用文件系统监听（如 `fs.watch`）实时检测文件变化（可选优化）

### 12.2 本地资源 HTTP 服务

#### API 设计

```
GET /api/local-video?path={encoded_path}

功能：
- 提供本地视频文件的HTTP访问
- 支持Range请求（断点续传）
- 支持视频流式传输
```

#### 实现要点

- **路径安全**：验证路径合法性，防止路径遍历攻击
- **文件存在性检查**：确保文件存在且可读
- **Range 支持**：支持 HTTP Range 请求，实现视频拖拽播放
- **MIME 类型**：正确设置 Content-Type

### 12.3 多站点资源选择

#### 选择逻辑

1. **默认选择**：优先选择第一个已完成的站点资源
2. **用户选择**：如果多个站点都有资源，提供选择界面
3. **质量优先**：可选按分辨率、文件大小等排序

#### 选择界面

- 显示所有可用站点
- 显示每个站点的资源信息（分辨率、大小、下载时间）
- 用户点击选择要播放的站点

### 12.4 播放地址转换

#### 本地路径转 HTTP 地址

```
本地路径：/data/videos/影片标题_2024/dyttzy_12345/episode_01.mp4
   ↓
HTTP地址：/api/local-video?path=/data/videos/影片标题_2024/dyttzy_12345/episode_01.mp4
```

#### 路径编码

- 使用 URL 编码确保路径中的特殊字符正确处理
- 示例：`/data/videos/影片标题_2024` → `/api/local-video?path=%2Fdata%2Fvideos%2F%E7%94%B5%E5%BD%B1%E6%A0%87%E9%A2%98_2024`

### 12.5 边界条件处理

**场景 1：本地资源文件不存在**

- **处理方式**：回退到在线播放，记录日志
- **用户影响**：自动切换，不影响播放

**场景 2：本地资源文件损坏**

- **处理方式**：检测文件完整性，损坏时回退到在线播放
- **用户影响**：自动切换，提示用户资源可能损坏

**场景 3：本地资源不完整（部分集数缺失）**

- **处理方式**：已下载的集数使用本地资源，缺失的集数使用在线资源
- **用户影响**：混合播放，体验略有影响

**场景 4：权限不足**

- **处理方式**：提示权限错误，回退到在线播放
- **用户影响**：需要修复权限问题

### 12.6 验收标准

- [ ] 本地有资源时优先使用本地资源播放
- [ ] 本地资源播放流畅，无卡顿
- [ ] 本地资源不存在时自动回退到在线播放
- [ ] 多站点资源可以选择播放
- [ ] 本地资源 HTTP 服务正常工作
- [ ] 支持视频拖拽播放（Range 请求）
- [ ] 显示资源来源标识（本地/在线）

## 15. 总结

### 15.1 核心价值

本功能通过本地资源下载和播放，解决了高峰期播放卡顿的问题，提升了用户体验。主要价值包括：

1. **播放流畅度提升**：本地资源播放无卡顿，体验显著提升
2. **自动化体验**：播放记录自动下载，用户无需手动操作
3. **多站点支持**：同一资源多个站点版本，用户可选择最优资源
4. **Docker 友好**：支持 Docker 部署，数据持久化，适合 NAS 等场景

### 15.2 关键设计决策

1. **混合下载策略**：手动下载 + 播放时下载 + 播放记录自动下载
2. **多站点资源分割**：每个站点独立存储，支持多源选择
3. **Docker 数据持久化**：通过 Volume 挂载实现数据不丢失
4. **资源刮削**：生成标准化元数据，与现有系统无缝集成

### 15.3 后续优化方向

1. **智能下载策略**：根据用户观看习惯，预测性下载
2. **资源质量优化**：自动选择最优质量的资源下载
3. **存储空间管理**：自动清理不常用资源，优化存储空间
4. **下载速度优化**：支持多线程下载、P2P 加速等
